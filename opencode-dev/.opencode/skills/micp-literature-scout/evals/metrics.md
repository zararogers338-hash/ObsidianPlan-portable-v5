# Metrics — micp-literature-scout

每项指标给出**测量方法**与**最低阈值**;`evals/run.py` 执行 cases.yaml 后调用
`metrics.py` 的 `measure()` 生成最终报告(写入 `evals/results/latest.json`)。

| 指标 | 测量方法 | 最低阈值 | 当前结果(2026-08-06) |
|---|---|---|---|
| M1 结构化输出通过率 | 每个 CLI 输出过 `schemas/output.schema.json`;通过数/总输出数 | ≥0.95 | 1.000 ✅ |
| M2 工具真实调用率 | 到达 handler 的 `search.*` 用例中,返回记录数/到达数(未到 handler 的 BLOCKED 不计) | =1.0 | 1.000 ✅ |
| M3 引用/数据可追溯率 | 返回记录中 DOI 结构合法数/总记录数 | ≥0.9 | 1.000 ✅ |
| M4 缺失输入识别率 | K 个必需字段逐一缺失→BLOCKED 且 detail 命名字段;命中数/K | =1.0 | 1.000 ✅ |
| M5 对抗用例拦截率 | 伪造 DOI、未知 action、契约冲突全部被拦(状态为 BLOCKED/FAILED/PARTIAL+错误) | =1.0 | 1.000 ✅ |
| M6 重复运行一致性 | 相同检索式两次独立进程:repro_id 相等且记录字节一致 | =1.0 | 1.000 ✅ |
| M7 平均失败恢复时间 | BLOCKED/FAILED 信封产生的墙钟毫秒,5 次均值 | ≤5000ms | ≈242ms ✅ |

## 测量要点

- **M2 的边界**:缺失输入/契约冲突/过短查询在 dispatch 前被 run() 拦截,未调用工具,
  不构成"工具尝试"——否则会错误拉低工具诚实度。只有实际到达 handler 的 `search.*`
  才算 attempt;attempt 必须返回记录才算 real call。
- **M3 的语义**:离线只能核验结构,因此可追溯=DOI 结构合法(离线规则判定
  `offline_unverified` 或 `verified`);伪造/非法结构不计入可追溯。
- **M6 的确定性**:离线 fixture + `repro_id`(查询规范化指纹)保证字节级一致;
  在线模式只保证"相同检索式可复现",不保证上游返回逐字节一致。

## 阈值选择依据

- M1/M2/M3/M4/M6 设为高门槛,因为这是受治理的检索能力——输出必须始终可机读、
  工具必须真实调用、引用必须可追溯、缺失必须被识别、检索必须可复现。
- M5 =1.0:对抗输入(伪造引用/未知命令/契约冲突)是审计底线,不容失守。
- M7 ≤5s:控制器等待 Skill 失败信封的最长容忍时间;本实现为亚秒级。
